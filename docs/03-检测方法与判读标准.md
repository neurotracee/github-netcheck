# 检测方法与判读标准

这份文档解释「为什么报告长这样、数字怎么来的、什么情况该信什么」。实现细节对不上时以代码为准
（`windows/netcheck.ps1` / `android/.../net/Probe.kt`）。

---

## 一、为什么分四段

浏览器打不开一个网站，可能是很多原因：域名没解析出来、端口连不上、TLS 握手被掐、请求发出去没回应、
服务器返回 500。只说「打不开」等于没说。所以每个点位按顺序测四段，**每段单独计时**：

| 段 | 做了什么 | 耗时含义 | 失败通常意味着 |
| --- | --- | --- | --- |
| DNS | `InetAddress` / `GetHostAddresses` 解析域名，只取 IPv4 | 解析耗时 | 断网、DNS 服务器不可用、DNS 污染 |
| TCP | 向解析出的 IP 的 443 端口建连 | 建连耗时（含一次 SYN/ACK 往返） | 端口被阻断、目标不可达 |
| TLS | 在这条 TCP 上完成 TLS 1.2 握手（**不校验证书**） | 握手耗时 | SNI 干扰、中间设备替换证书、协议被重置 |
| HTTP | 发一个 `GET` 请求，等到收到第一个字节 | TTFB | 链路被掐断、服务端无响应 |

四段相加不等于总耗时——总耗时包含进程调度、字节读取、字符串处理的开销，只作参考。
**判读只看 TCP 那一段**：它最能反映「链路能不能用」，且不受服务端逻辑影响。

### 几个刻意的取舍

- **先解析再连 IP**：TCP 段计时用解析出来的 IP 直连，避免把第二次 DNS 时间算进建连。
- **忽略证书校验**：目的是测「连通性」，不是测「证书是否合法」。代价是证书链有问题时报告仍显示正常，
  这一点在 README 的「已知限制」里写明了。
- **固定 TLS 1.2**：桌面端与安卓端都强制 TLS 1.2。理由：14 个点位全部支持 1.2，固定版本能让两台设备的
  握手往返次数一致，数值才可比。若有站点只支持 1.3，会被判「受限」——目前点位里没有这种站点。
- **超时 3 秒**：单段上限 3 秒。网络特别差时，本来 5 秒能连上的也会被判失败，重跑一次看是否稳定。

## 二、评级阈值怎么定的

| 标签 | 阈值 | 为什么这么定 |
| --- | --- | --- |
| 优秀 | TCP ≤ 120 ms | 与国内站点（百度、阿里）同城/邻省的典型建连水平 |
| 良好 | ≤ 400 ms | 跨省 + 一次中转，日常可用 |
| 一般 | ≤ 1000 ms | 能用但每次请求都要等，页面会明显卡顿 |
| 较慢 | > 1000 ms | 接近「不可用」，多数请求会超时重试 |
| 受限 | TCP 通、TLS 失败 | 最典型的「被墙」形态：端口通、握手被掐 |
| 不通 | TCP 都连不上 | 完全阻断，或本地网络本身有问题 |

阈值只看 **TCP 建连**，不看 TLS/HTTP。原因：后两段受服务端与中间设备策略影响大，波动也大，
用它们做评级会让同一网络下的结论每次都不一样。

判定顺序是**先看 TCP 再看是否成立**：

```
TCP 失败            → 不通
TCP 成功、HTTP 失败  → 受限
TCP 成功、HTTP 成功  → 按 TCP 毫秒数分四档
```

这就是 `Verdict.of()` / `Get-Verdict` 的全部逻辑，两端逐字对齐，单元测试覆盖了每个边界（120/121/400/401/1000/1001）。

## 三、进度条不是「速度」

报告里每条右侧的细条**不是带宽**，是把 TCP 建连耗时按 0–500 ms 映射成 0–100% 的视觉长度，
不足 4% 按下限 4% 显示；失败时满格并压成半透明（表示「这一项没测出来，不要看长度」）。

要看真实带宽得传大文件，本工具不做这件事——它测的是「这条路通不通、通的话有多快起步」。

## 四、DoH 对照是干什么的

国内网络环境下，最容易被忽略的一层是 **DNS 被改写**：域名解析出来的 IP 不是真的，于是后面三段怎么测都白搭。
所以每个点位额外做一次对照查询：

```
本机解析（系统 DNS / hosts）  →  IP_A
阿里公共 DNS 加密查询（DoH）   →  IP_B
```

| 报告里的显示 | 含义 |
| --- | --- |
| `DoH 一致` | 两边解析到同一个 IP，本机 DNS 正常 |
| `DoH 真实解析 x.x.x.x` | 两边不一致：本机解析被改写、被污染，或走了本地反代 |
| 没有这行 | 对照查询本身失败（连不上 DoH 端点），此时不要拿它下结论 |
| 本机 IP 显示 `127.0.0.1` | 域名被 hosts 指向本机，流量走的是本地反代（瓦特工具箱这类工具的标准做法） |

实现差异：桌面端先解析 `dns.alidns.com` 再连（DNS 已被污染时可能查不到）；
安卓端**直连 223.5.5.5**（SNI 仍写 `dns.alidns.com`），因此对照值更可靠。这是两端唯一有意的能力差异。

## 五、环境检查项的含义

| 项 | 桌面端怎么读 | 安卓端怎么读 | 看到什么要警惕 |
| --- | --- | --- | --- |
| 系统代理 | 注册表 `Internet Settings\ProxyEnable/ProxyServer` | `ConnectivityManager.getDefaultProxy()` | 开了代理但本工具不走它，测的是直连——数值差是正常的 |
| hosts 本地映射 | 读 `%WINDIR%\System32\drivers\etc\hosts`，只看指向 127.0.0.1/0.0.0.0/::1 的行 | 读 `/system/etc/hosts` | 有映射且 IP 显示 127.0.0.1：反代可能没在转发 |
| 本机 443 监听 | `Get-NetTCPConnection -State Listen -LocalPort 443` | 无法读取（平台限制） | 有程序监听 + hosts 有映射 = 本地反代正在运行 |
| VPN | 不检测 | `NetworkCapabilities.TRANSPORT_VPN` | 开启时 socket 被系统层接管，测到的是「走规则后」的结果 |
| 私有 DNS | 不检测 | `LinkProperties.isPrivateDnsActive / privateDnsServerName` | 开着 DoT 时解析路径与本机不同，会影响 DNS 段 |
| DNS 服务器 | `Get-DnsClientServerAddress` | `LinkProperties.dnsServers` | 出现陌生 IP，可能与 DNS 劫持/加速工具有关 |

## 六、怎么用它做对比实验

最实用的一种用法：**同一条链路，两种状态，两份报告**。

1. 关掉所有加速/代理/VPN，跑一次，存为 `off.html`；
2. 打开加速工具（hosts 模式或系统代理模式），再跑一次，存为 `on.html`；
3. 两份并排看：
   - TCP 段普遍下降 → 加速生效；
   - TCP 没变、但「受限」变成「优秀/良好」→ 只是把 TLS 握手救回来了；
   - IP 变成 127.0.0.1、TCP 很低但 HTTP 变慢 → 走的是本地反代，看到的是「到反代」的延迟，不代表到真实服务器；
   - 个别点位仍然「不通」→ 加速规则没覆盖那个域名。

安卓端如果开着 Clash 类 VPN，第一份报告就已经是「走规则后」的结果，此时要对比得先关 VPN 用移动数据跑一次。

## 七、这份报告不能回答什么

- **不能测带宽、不能测丢包率、不能测抖动**（只测单次建连）。
- **不能判断「网站是不是挂了」**——只测到「我这台设备到那个域名通不通」。
- **不能定位到具体网络设备**（哪一跳、哪个运营商节点）。
- **不能替代抓包**（要看 TLS 里发生了什么，得用 Wireshark 之类）。
- **证书问题看不出来**（故意忽略校验）。
